---
name: agent-workflow
description: Delegate bounded implementation, design, review, or peer analysis to configured local AI CLIs through Agent Workflow when the user requests collaboration or a project workflow calls for it. Ordinary development does not automatically start workers.
---

<!-- installation -->

Use the installed entrypoint above when present. Otherwise run `node` with the absolute path to [aw.mjs](aw.mjs) beside this SKILL.md; locate it relative to this skill's path, not the current working directory. It resolves the registered checkout and host file. `AW_ROOT` overrides the checkout; `AW_HOST_CONFIG` or `--host-config FILE` overrides the host file. Defaults are `~/.config/agent-workflow/host.json` on Linux/WSL and `%LOCALAPPDATA%/agent-workflow/host.json` on Windows. Do not install or enable providers implicitly.

Use `prepare --workflow NAME --cwd PROJECT` when the project has an established workflow mapping; otherwise use `prepare --role ROLE --cwd PROJECT`. It returns the effective binding and only that role's instructions plus applicable project instructions. Follow the returned instructions in the current task for a host role; for a runnable worker role, submit with the same workflow or role. Do not reread every role or the design documents. `roles` gives compact choices when selection is needed.

Bindings determine execution location and access. A host role stays in the current agent without changing its model setting. Read-only workers return advice; the `executor` worker can edit in an owned worktree and complete a supervised verification loop. Inspect `prepare` for actual capabilities. For implementation delegation, read [execution.md](references/execution.md). `providers` and `models PROVIDER --refresh` diagnose a specific capability or catalog issue; configured names are not proof of server support. Do not change bindings, install a profile, loosen permissions, or switch a paid provider merely to make a task runnable.

Submit a JSON request file in the project's ignored run/cache directory or a private temporary directory. Required fields: `goal`, `acceptance` (nonempty string array), `read_paths` (paths within cwd). Optional: `evidence` (reference strings), `stage` (`independent` or `cross-review` for read-only), `source`, `timeout_seconds`, and `handoff`. The handoff's optional `context`, `current_state`, `attempted`, `decisions`, and `constraints` are string arrays. Preserve the task's intent: an investigation stays an investigation. Supply relevant paths, prior failed approaches and acceptance; avoid full chat history. Use a stable request ID for retries of the same intent.

`run --role ROLE` or `run --workflow NAME`, together with `--cwd PROJECT --request-file FILE --request-id ID`, returns a task ID. Persist it with the current task. `wait TASK --timeout 45` is bounded; a wait timeout does not cancel the worker. Continue independent work while it runs. Reuse completion notifications if the calling host supplies them; AW's standalone CLI currently uses bounded waits, so do not assume a callback exists or repeatedly issue immediate status checks. `result TASK` returns a summary and report reference; use `--cursor 0` and later cursors for relevant missing detail. Completed does not mean accepted: review verdicts, blockers, unverified checks and uncertainties still govern acceptance.

`followup TASK --request-file FILE --request-id NEW_ID` explicitly continues the stored provider session, role and model, including a failed turn that retained a resumable handle. Send only changed evidence or specific disputes. Use `recover TASK` for an unknown/interrupted attempt. Unknown still occupies a worker slot; do not submit the same intent under a new ID automatically. `cancel TASK` retains artifacts and can record cancellation before a late launch receipt arrives. No automatic quota retries or session forks.

For advice, ask one focused question with the alternatives already considered. Continue the same advisor for follow-ups on that question. For complex design, request constraints, tradeoffs and acceptance, then implement in the host or hand a bounded work package to an enabled executor. Read-only reviewers use supplied runtime evidence and cannot run tests themselves. Small changes do not require a design/review round. Additional independent opinions should have an explicit purpose and stopping point; do not start an open-ended committee.

For an established dual-analysis workflow, freeze the host's initial judgment, send the peer only common evidence first, then make one focused cross-review of material premises. The host produces the final conclusion under the original project skill. No trading authority is introduced.
