## Host routing

The current Codex conversation normally handles basic and everyday development itself. Configure external models mainly for difficult escalation, design, review, peer analysis or specialist execution. For a substantial task, check `routing` once per host configuration/session. When enabled, classify it using existing context and call `route --kind code|artifact|design|review|analysis --complexity simple|standard|complex --cwd DIR`; follow its configured role. Read [routing.md](references/routing.md) for classification, escalation and stopping rules. Do not call a separate classifier model. User-specified roles/providers, an established project workflow and applicable project skills take precedence. Trivial replies/edits need no worker. When routing is disabled, delegate only when the user or project workflow requests it. A worker selected for escalation/specialist work gets one complete bounded work package; the host coordinates, checks and integrates rather than duplicating its implementation.

Use `prepare --workflow NAME --cwd DIR` for an established project workflow; otherwise use `prepare --role ROLE --cwd DIR`. For non-Git output work add `--workspace-mode directory`. Prepare returns the effective binding, that role's instructions and applicable project instructions. Follow these in the current task for a host role; submit a runnable worker with the same role/workflow. Do not reread every role or design document. `roles` gives compact choices when needed.

Bindings determine execution location and access. A host role stays in the current agent **without changing or establishing the current conversation's model**. Read-only workers return advice. Writable implementation roles can use `git-worktree` or `directory` and complete a supervised verification loop through Claude, Codex, OpenCode, DSH or ACP. Inspect `prepare` for access, permissions and capabilities; read [execution.md](references/execution.md) before implementation delegation. `providers` and `models PROVIDER --refresh` diagnose a specific issue; configured names are not proof of server support. Do not change bindings, install a profile, loosen permissions, or switch a paid provider merely to make a task runnable.

## Explain actual collaboration

Before a worker call, briefly tell the user its role, CLI, requested model/effort, assigned work and why it fits. Announce a follow-up or escalation with the failed check/new evidence and what changes. Bounded automatic verification repairs stay with the same model; report the actual repair count when the result arrives. A preparation/catalog probe is not a model task.

**Every final reply after dispatch must include a concise collaboration account**, alongside the outcome: actual roles and CLI/models invoked, their contributions, failures or escalation if any, and what the host verified/integrated. Use `run`/`status`/`result`'s `dispatch`, task state and execution report as evidence. `requested_model` is the launch selection; `observed_model` is what the CLI reported and can be null. Do not invent a confirmed model/effort or credit a planned, blocked or setup-failed call as completed work. Mention the relevant task ID/report when useful; do not dump raw prompts/logs. One line is enough for one worker, e.g. “基础开发师（DSH / 配置模型，low）完成脚本；主控核对文件和运行结果。共 1 次执行。” Include actual failures even if the host ultimately completes the task. If no worker ran, do not fabricate a collaboration section.

## Submit and continue

Submit a JSON request file in the project's ignored run/cache directory or a private temporary directory. Required fields: `goal`, `acceptance` (nonempty string array), `read_paths` (paths within cwd). Optional: `evidence` (reference strings), `stage` (`independent` or `cross-review` for read-only), `source`, `timeout_seconds`, and `handoff`. The handoff's optional `context`, `current_state`, `attempted`, `decisions`, and `constraints` are string arrays. Preserve the task's intent: an investigation stays an investigation. Supply relevant paths, prior failed approaches and acceptance; avoid full chat history. Use a stable request ID for retries of the same intent.

Read-only tasks default to `read_mode: evidence`: AW supplies the declared UTF-8 files, with optional `read_ranges: [{path, start_line, end_line}]`, and disables filesystem exploration. Supply relevant files/ranges and existing verification; missing evidence should produce an explicit gap. Oversized, directory or binary inputs fail before a model task. When autonomous file exploration is needed, explicitly select `read_mode: native` and inspect `prepare.controls`; native path enforcement differs by CLI. Writable tasks use native tools. Never silently widen evidence scope after a failure.

`budget` can lower the configured model-step, tool, output-token, CLI-call, duration and read-byte limits. A work package shares its budget across followups and automatic verification repairs; do not create a new ID to reset exhausted work. Check `remaining_budget`, `telemetry` and `usage_complete` before continuation. Missing tokens are unknown, not free; observed counters cannot guarantee an exact provider billing cap. See [worker-limits.md](references/worker-limits.md) for the request and recovery details. AW generates the delivery schema and performs bounded local JSON recovery; do not ask another model to reformat an otherwise complete report.

`run --role ROLE` or `run --workflow NAME`, together with `--cwd PROJECT --request-file FILE --request-id ID`, returns a task ID. Persist it with the current task. `wait TASK --timeout 45` is bounded; a wait timeout does not cancel the worker. Continue independent work while it runs. Reuse completion notifications if the calling host supplies them; AW's standalone CLI currently uses bounded waits, so do not assume a callback exists or repeatedly issue immediate status checks. `result TASK` returns a summary and report reference; use `--cursor 0` and later cursors for relevant missing detail. Completed does not mean accepted: review verdicts, blockers, unverified checks and uncertainties still govern acceptance.

`followup TASK --request-file FILE --request-id NEW_ID` explicitly continues the stored provider session, role and model, including a failed turn that retained a resumable handle. Send only changed evidence or specific disputes. Use `recover TASK` for an unknown/interrupted attempt. Unknown still occupies a worker slot; do not submit the same intent under a new ID automatically. `cancel TASK` retains artifacts and can record cancellation before a late launch receipt arrives. No automatic quota retries or session forks.

For advice, ask one focused question with the alternatives already considered. Continue the same advisor for follow-ups on that question. For complex design, request constraints, tradeoffs and acceptance, then implement in the host or hand a bounded work package to an enabled executor. Read-only reviewers use supplied runtime evidence and cannot run tests themselves. Small changes do not require a design/review round. Additional independent opinions should have an explicit purpose and stopping point; do not start an open-ended committee.

For an established dual-analysis workflow, freeze the host's initial judgment, send the peer only common evidence first, then make one focused cross-review of material premises. The host produces the final conclusion under the original project skill. No trading authority is introduced.
